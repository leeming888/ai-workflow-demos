# Demo 1 · AI 自动化巡检系统（可运行）

> **解决什么问题**：公司的 AI 自动化 / 定时任务 / 爬虫脚本，跑着跑着就悄悄坏了 —— 没人发现，直到某天发现"已经停了两周"。
>
> **本 Demo 检查 12 个维度**，输出人读报告 + 机器读 JSON。

---

## 真实背景（这不是玩具，是明哥自己踩出来的）

> **背景**：明哥的 `weekly_review.py` 曾**静默失败 2 周而没人发现**，因为失败在一个没人看的地方。
>
> 后来又复发 **3 次同类问题**，每次都是同一个根因：
>
> | 日期 | 缺口 | 后果 |
> |---|---|---|
> | 2026-10-17 | 以为自动化是每天跑，实际是**每周日 22:00** | 按 24h 判 → 永远显示 ✅，掩盖真漏跑 |
> | 2026-10-21 | 接单工作流在**另一个工作区**，产出不在本区 | 云端有 ACTIVE，面板完全没跟 |
> | 2026-10-30 | 付费产品自动化在**第三个工作区**，目录首跑前不存在 | 同上，第三次复发 |

**"漏监控比误报更危险，因为它永远显示一切正常。"**

## 检查维度（34 个函数 / 12 类）

| # | 维度 | 检查什么 | 抓过什么坑 |
|---|---|---|---|
| 1 | **产出新鲜度** | 每个自动化的产出文件 mtime vs 约定周期 | 静默失败 2 周 |
| 2 | **调度器失败** | Windows 任务计划 / 云端自动化的退出码 | 调度成功但产出为空 |
| 3 | **"成功但无产出"** | 调度器说成功，产出文件却没有 | **最难查的一类** |
| 4 | **自我覆盖** | 自动化在自己产出目录里又扫到自己 | 重复计入 |
| 5 | **漏跑识别** | 机器关机导致的天数 vs 应跑天数 | 关机日被误判为正常 |
| 6 | **崩溃检测** | 上次运行的异常堆栈 | 脚本 crash 但没人看 |
| 7 | **机器开机窗口** | uptime 反推关机时段 | 解释"为什么漏跑" |
| 8 | **磁盘健康** | 关键目录体积 + 剩余空间 | Codex runtime 堆积 |
| 9 | **回收站** | 删除后空间没释放的真凶 | 回收站不释放空间 |
| 10 | **日志健康** | WorkBuddy 日志体积/增长 | 日志撑爆磁盘 |
| 11 | **Git 状态** | 未提交改动 / 未跟踪文件 | 改完没提交，丢代码 |
| 12 | **计划任务对账** | 云端 ACTIVE vs 本地 schtasks vs 实际产出 | **三次覆盖缺口的根源** |

## 运行方式

```bash
python check_automations.py            # 终端输出 + 写 dashboard.md + automation_status.json
python check_automations.py --quiet    # 只写文件不打印（适合挂定时任务）
```

**输出物**
- `dashboard.md` —— 人读：每个自动化的状态表 + 异常清单 + 建议动作
- `automation_status.json` —— 机器读：可接告警（企微机器人 / 邮件 / Webhook）

## 为什么值得单独卖这个

**1. 它解决的是老板最怕的事**
不是"帮我做内容"，是"**别让我系统悄悄坏掉**"。省下的是"发现问题时已经过了两周"的损失。

**2. 它有明确的数据证据**
明哥这套是**跑了 13 天、真实踩了 3 次坑**才磨出来的。同行写不出"三工作区覆盖缺口"这种只有真跑过的人才知道的检查项。

**3. 它天然带复购**
巡检系统是要一直跑的 → 月度维护费是自然续费，不是硬推销。
